# macOS 四路中转备用：固定最终出口

[返回 README](../README.md)

## 当晚补充：界面操作会破坏脚本链路

初次短测通过后，实际使用发生过回归：客户端生成文件中的五个 SOCKS5 节点（一个基准节点、四个完整链路节点）全部丢失 `dialer-proxy`。节点名称和四路分组仍在，不能据此认为链式配置还在。代理认证与端点没有变化，独立实例仍可连接。

核对 Clash Verge Rev **v2.5.2 源码**发现：

- [运行配置更新](https://github.com/clash-verge-rev/clash-verge-rev/blob/v2.5.2/src-tauri/src/config/runtime.rs)的 `update_proxy_chain_config` 会先移除所有节点的 `dialer-proxy`，传入空值时不会重新建立链路。
- [代理页面](https://github.com/clash-verge-rev/clash-verge-rev/blob/v2.5.2/src/pages/proxies.tsx)退出内置链式模式时调用上述清除操作。
- [手动链式分组页面](https://github.com/clash-verge-rev/clash-verge-rev/blob/v2.5.2/src/components/proxy/proxy-groups-chain.tsx)在规则模式更换目标组时也调用清除操作。

因此，脚本管理四路链路时，**不要同时使用内置手动链式编辑器**。退出该编辑器后，必须再到“订阅 → 重新激活当前配置”，让脚本重建字段；单纯切到规则模式不会自动修复被删除的链路。

还观察到两个 fallback 组的 `fixed` 字段非空，表示被手动固定。修复时取消固定，复核两个组的 `fixed` 均为空。使用自动备用时不要手点某个成员把它固定住。界面蓝色选中背景表示当前使用，不等同于红色图钉表示的手动固定。

正确界面是标题“代理组”、顶部“规则”选中、“链式代理”按钮未启用，两组无红色图钉。规则模式按规则使用 `Claude-Fixed-Egress`，无需再“选择整个组”。

验收已增加两个不可省略的项目：**客户端最终生成文件中的逐节点 `dialer-proxy` 映射**，以及**运行态 fallback 的 `fixed` 为空**。重新激活、切换页面后再检查；只验脚本输出、节点数量或 IP 一次回显都不够。修复没有升级或修改客户端程序；内置编辑器清除字段的行为仍然存在，不应宣称此风险已从软件中消除。

本段是对初次交付结论的修正：初次结果仅证明当时短测通过，并未覆盖上述界面操作。

## 本次变更

在 `origin/main` 的 `43fbd55`（Windows 三路备用）基础上，为一台 Mac 配置四路中转，并保留此前的脱敏文档工作。这里记录的是 **2026-10-06 的本机短时验收**，不是所有设备的部署保证，也不是账号可用或防封证明。

```text
普通应用 → HTTP / TUN → 完整链路 fallback
                           ├─ 中转 A → 同一个固定 SOCKS5
                           ├─ 中转 B → 同一个固定 SOCKS5
                           ├─ 中转 C → 同一个固定 SOCKS5
                           └─ 中转 D → 同一个固定 SOCKS5 → 网站

AdsPower 自填 SOCKS5 → 只对该 SOCKS5 服务器的 TCP 地址和端口
                      使用 Relay-Auto → 同一个固定 SOCKS5 → 网站
```

最终出口不参与轮换。普通业务组仅包含完整链路，不包含 DIRECT 或裸中转。应用自管 SOCKS5 的连接不能再套一次 SOCKS5，否则会重复代理。

## 为什么选四路，而不是把订阅全塞进去

本次选择现有订阅里的四个指定节点：两组新加坡、一组日本、一组香港中转。探测时四组服务器地址集合不同；另一个名字不同的新加坡节点与现有服务器重合，因此未算成独立备用。

这四路仍来自同一个供应商，不能防御供应商整体停服、套餐到期、固定 SOCKS5 故障、本地断网或目标服务故障。不同地区的节点名称，也不证明国内入口和骨干线路完全独立。增加第二供应商需要单独授权、核对凭据及防火墙规则，不会自动购买。

## 实施要点

1. 检查磁盘配置、内核运行态、GUI 三者。此次磁盘写着规则模式，但运行态和 GUI 处于全局模式，并选择裸中转；独立测试确认原固定出口可用后，已在 GUI 和运行态恢复规则模式。
2. 备份脚本、配置和 PF 守护脚本。涉及秘密的副本仅留本机，目录权限受限，不随文档发布。
3. PF 从一个中转域名扩展到四个明确域名；仍只允许中转的指定 TCP 端口及既有引导 DNS 例外，不开放任意公网连接。每个域名独立保存上次成功解析结果，单个解析失败不清空其余线路。DNS 定时刷新不等于域名或 IP 永远不变。
4. 完整链路组采用有序 `fallback`；健康检查经过中转、SOCKS5 认证和 HTTPS 目标。生产参数为 60 秒检查、8 秒超时，不能把它解释成“60 秒内必定恢复”。检查目标本身故障也可能导致误判。
5. AdsPower 和已有明确获授权的应用例外使用裸中转备用组；普通默认流量仍走固定出口。**有这些例外就不能声称电脑所有流量均为美国出口。** 公开模板不自动加入任何个人应用例外。
6. 不强制更换 TUN 设备名，不更改客户端版本。本机继续使用原有 `utunN` 和 Mihomo v1.19.29；客户端重新生成配置后，检查四路分组仍在。
7. 部署时安排独立的 180 秒未确认自动回滚；正向验收成功后才提交，保留旧单线路配置与 PF 备份。

### AdsPower 健康检查的边界

普通业务组检查的是完整链路；`Relay-Auto` 检查裸中转到 HTTPS 探测站的连通性。两组独立选择，因此不能保证遇到“某中转能访问探测站，但唯独无法连接 SOCKS5 服务器”时同步切换。

本次模拟的是中转整体不可达，应用自管 SOCKS5 路径通过了相应切换测试。没有用 AdsPower 的实际浏览器窗口或账号会话做验收，也没有宣称解决浏览器渲染进程崩溃。需要更强的一致性时，应另做终点感知的运输组同步设计与测试，不能把普通延迟检测当成此项已完成。

## 验收结果（地址与凭据已脱敏）

每路均独立检查两个 HTTPS IP 回显服务，最终回显一致、地区为 US；健康检查返回 204。

| 中转顺序 | 单次 IP 回显总耗时 | 完整出口一致 |
| --- | --- | --- |
| A：现有新加坡 | 2.12 秒 | 是 |
| B：另一组新加坡 | 2.24 秒 | 是 |
| C：日本 | 2.27 秒 | 是 |
| D：香港 | 3.14 秒 | 是 |

这些是单次小请求总耗时，不是 Ping、带宽测试、长期分位数或业务首字时间，不能据此承诺业务不卡顿。

故障注入在单独的回环端口测试实例完成，TUN 关闭；将前若干个中转指向本机不可连接端口。测试实例使用 10 秒检查、4 秒超时，与生产参数不同，没有中断生产线路来模拟故障。

| 隔离故障场景 | 普通完整链路 | 模拟应用自管 SOCKS5 |
| --- | --- | --- |
| 无故障 | A，同一固定出口 | 同一固定出口 |
| A 不可达 | B，同一固定出口 | 同一固定出口 |
| A、B 不可达 | C，同一固定出口 | 同一固定出口 |
| A、B、C 不可达 | D，同一固定出口 | 同一固定出口 |
| 四路全不可达 | 请求失败，无其他出口回显 | 请求失败，无其他出口回显 |

生产复核：HTTP 入口、无显式代理的 TUN 请求、应用自管 SOCKS5 请求和第二个回显服务均得到同一个固定美国出口。客户端重新生成了 YAML，四路分组、规则模式和现有 TUN 保持有效。

没有重启整台电脑，没有测睡眠唤醒、换 Wi-Fi、长期连续会话、目标账号状态或浏览器 WebRTC；不能拿短时测试替代这些验收。

## 公开模板与复现

[四路模板](../examples/fixed-egress-failover.js) 默认 `enabled: false`，不会修改输入。部署必须先在私有副本填写精确白名单、端口及已存在的出口节点，再启用；`expectedIPv4` 在此兼容模板中表示 **SOCKS5 服务器地址**，不执行远端回显校验，验收时必须另行比较真实出口。

保留 Windows 原始三路验收记录：[Windows 实施](2026-10-04-windows-fixed-egress.md)、[Windows 证据边界](2026-10-04-verification.md)。当前公开模板已扩为四路，并增加默认关闭、重复白名单校验、重复运行安全和保留平台 TUN 设置。这些变化不追溯改变旧报告的测试数量或部署结果。

```sh
node --test tests/fixed-egress-failover.test.cjs
node tests/verify.cjs
```

公开测试使用合成节点，不读取本机凭据、不改变网络。私有候选配置还必须用已安装内核执行 `-t` 检查，再进行正向和故障验收。

注意：模板保留既有中转 TLS 设置。本次私有订阅原本含 `skip-cert-verify: true`，未新增或扩大该设置；这仍是未解决的中转认证风险。不要因此把中转证书标为已验证。最终 HTTPS 校验与中转 TLS 校验是两回事。

## 日常使用和回滚

- 保持规则模式，勿手选全局裸中转；全局模式会绕过分流规则。修改后重新检查实际出口。
- 不需要手工轮换四路；fallback 优先选择排序靠前且探测可用的线路，不是最快线路竞赛。
- 切换只帮助新连接，已有 TCP、流式会话不会无损迁移；故障时仍可能需要刷新或重连。
- 四路全失败时，即便界面还显示第一个节点名，也不能据此认为网络可用；应看真实请求结果。不要添加 DIRECT 或不同 IP 出口来凑“全绿”。
- 回滚先恢复旧单线路客户端配置并验证，再恢复较窄的 PF 中转白名单。不要直接关闭整个 PF 或清空系统其他规则。
- 备份、完整配置、代理密码、订阅 URL 和原始回显日志不上传仓库。
